# 真·端到端「3 DB + LLM」实测(LoCoMo 对话记忆)

全部真实、全部本地、无伪造:
- **LLM**:OpenBMB **MiniCPM5-1B**(Q4 GGUF,llama.cpp)— 对每个对话 turn 抽取原子事实
- **向量库**:Alibaba **Zvec**(HNSW,cosine)— 存取事实/turn 的稠密向量
- **KV**:**LMDB** — 存正文
- **嵌入**:bge-small-en-v1.5(ONNX,384维)

脚本:`bench/e2e_3db_llm.py`。评测口径:evidence recall@5 —— 检索到的条目的来源 turn 是否覆盖 LoCoMo 标注的证据 dia_id。

## 最终测试数据

| 架构(2 会话 / 301 问题 / 788 turn,真机) | evidence recall@5 | 全证据@5 |
|---|---|---|
| **A. raw-turn + Zvec**(向量库,无 LLM) | **0.485** | 0.452 |
| **B. 3DB+LLM:MiniCPM-1B 提取 + Zvec** | **0.193** | 0.179 |
| (参考)我们的混合 BM25+bge+图 | **0.560** | 0.521 |

**LLM 提取成本:** 788 turn 提取耗时 **435 s(0.55 s/turn)**;只产出 **333 条事实**——MiniCPM-1B **丢弃了 58% 的 turn**(判为无事实)。

## 结论(真实、反直觉)

1. **用 1B 模型搭的完整「3DB+LLM」反而最差**:evidence recall@5 仅 **0.193**,远低于不带 LLM 的 raw-turn 向量检索(0.485),更低于我们的混合(0.560)。
2. **原因**:1B 模型的抽取是**有损**的——丢掉 58% 的 turn,这些 turn 一旦是证据就**永远无法被召回**;加上抽取本身质量一般(漏掉明显事实)。任何「先抽取再检索」都被这道信息损失卡住。
3. **那 Mem0/HippoRAG 的 92.5 怎么来的?** 它们用 **GPT-4 级**强模型抽取,且测的是**下游问答准确率**(干净事实喂给大模型作答),不是这里的检索召回。**强模型 + QA 口径**才是重型设计的主场;**1B + 检索召回**口径下它是负优化。
4. **工程成本**:LLM 抽取(0.55 s/turn)是建库的主导开销;对万级 turn 的语料就是小时级。

## 给你的直接答复
- 「3DB+LLM」**现在是真实端到端实测了**(Zvec + MiniCPM-1B + LMDB + bge,全本地真跑)。
- 在**本地 1B + 对话检索**这个现实设定下,它**打不过**我们更简单的混合方案(0.19 vs 0.56),且更慢更重。
- 它要赢,得满足两个前提:**(a) 换强 LLM 抽取**(非 1B),**(b) 评的是问答准确率而非检索召回**。否则「LLM 提取」是在丢信息。

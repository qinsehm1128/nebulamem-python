# **2. 产品背景与痛点分析 (Product Background & Pain Points)**

## **2.1 市场现状**

现有的 RAG (Retrieval-Augmented Generation) 与 Agent 记忆库（如早期 MemGPT [Letta GitHub](https://github.com/letta-ai/letta) 或 2026年爆火的 [MemPalace](https://github.com/mempalace/mempalace)）在实际部署与应用中面临两个核心挑战：

1.  **基础设施沉重**：大多数方案需要繁重的 Docker 容器或外部数据库服务支撑，不符合本地轻量化工具的需求。
2.  **事实状态冲突**：当开发者在不同语境间切换（例如从 Python 项目切换到 Rust 项目）时，传统的向量检索往往因语义相似性导致新旧上下文污染，无法有效区分当前有效事实。

## **2.2 痛点解决方案**

NebulaMem 提供一种完全嵌入应用程序（In-Process）的数据库存储方案。系统废弃了传统的外部数据库依赖，直接基于 Zvec 与 LadybugDB (或其嵌入式等价物) 构建。通过轻量级的图-向量融合推理技术，引入**侧向抑制边（Inhibitory Connections）**。该机制能在毫秒级内识别并自动消解陈旧或冲突的记忆，确保记忆状态的实时准确性。

# **3. 核心产品愿景 (Core Product Vision)**

NebulaMem 旨在利用本地原生语言实现一套完全运行在用户本地终端环境下的记忆系统。该系统模拟人类大脑的"星域放电"与"联想扩散"机制：

  - **极致性能**：依托进程内向量检索与轻量级图拓扑计算。
  - **联想扩散**：实现秒级更新与毫秒级记忆联想。
  - **本地优先**：确保用户数据不出本地，实现隐私与效率的平衡，为智能体提供永不混淆的事实记忆支撑。

# **4. 关键功能性需求 (Functional Requirements)**

## **F-101: 进程内向量原子检索 (In-Process Vector Retrieval)**

  - **描述**：利用语义定位能力，在海量记忆库中快速找出与当前问题最相关的 1-3 个“锚点星点（Seed Nodes）”。
  - 要求：采用进程内 dense 向量极速检索，并利用预写日志机制保证本地持久化的数据一致性，实现零外部依赖的原子索引。

## **F-102: 带权关系星轨拓扑与扩散 (Weighted Graph Topology & Spreading Activation)**

  - **描述**：基于列式图表引擎存储 MemoryNode 与 LINK 关系表，通过原生的嵌入式查询完成图拓扑传导，构建动态的“星座图景”。
  - **算法细节**：能量在沿边扩散过程中必须遵循非线性衰减模型，以保证激活范围的合理性。

## **F-103: 陈旧记忆侧向抑制 (Lateral Inhibition)**

  - **描述**：支持用户或系统自动声明"状态升级"（例如：旧节点 Python 被新节点 Rust 覆盖）。
  - **要求**：在新旧冲突节点间建立 inhibitory 抑制边。当新事实节点被激活点亮时，释放负向能量，使旧的事实节点迅速熄灭，防止干扰。

## **F-104: 异步梦境整理与 Wiki 编译 (Asynchronous Consolidation & Compiler)**

  - **描述**：在系统 CPU 资源空闲时，自动执行知识蒸馏，合并冗余事实。
  - **输出规范**：将高频激活的节点拓扑编译成高内聚的 Markdown 文档，遵循 [Andrej Karpathy's LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) 规范，直接作为提示词喂给 LLM。

# **5. 非功能性需求 (Non-Functional Requirements)**

## **5.1 进程内本地优先 (In-Process & Local-First)**

系统严禁调用任何外部数据库网络端点，且无外部 daemon 常驻。所有持久化操作基于本地文件存储。通过列式存储与进程内调用，将单机内存开销降至最低，实现 100% 本地化运行。

## **5.2 极速响应 (Latency)**

单次完整的记忆检索流程（包含 Vector Search 与 3 轮图激活扩散）的总开销必须控制在 **15ms** 以内，以确保不会对 LLM 的首字生成延迟（TTFT）产生可感知的影响。

## **5.3 类型安全 (Type Safety)**

核心 API 接口及底层实体数据结构必须提供完善的类型定义，确保开发者的集成体验。

# **6. 边缘情况处理与消解方案 (Edge Case Handling)**

## **6.1 记忆循环扩散隔离**

为防止图结构中的环路导致无限扩散：

  - **步数限制**：严格限制 Spreading Activation 的最大步数（默认不超过 3 步）。
  - **能量衰减**：每一轮能量传导必须叠加强制的衰减因子（Decay），从物理层面避免堆栈溢出。

## **6.2 极寒突触清理 (垃圾回收)**

  - **权重衰减**：边权重会随时间或未点亮频率自然下降。
  - **自动剔除**：当节点或边的权重低于阈值 **0.1** 时，系统自动执行清理操作。此举可保障本地存储文件的精简与高能效运行。

# NebulaMem — 混合(词法+向量)真实测试结果与工程分析

> 全部为真机实测,**无文件过滤、无人工词库**(那会造假)。覆盖三类真实记忆:多跳事实(HotpotQA)、长对话(LoCoMo)、代码项目(sub2api)。

## 1. 加入向量模型,提升多少?(三域实测)

种子用 BM25,向量用 **bge-small-en-v1.5**(130MB,ONNX,CPU,无 torch),int8 量化,`hybrid = 0.5·BM25 + 0.5·cosine`。

| 领域 | 指标 | BM25 | 纯向量(小模型) | **混合** | 混合 vs BM25 |
|---|---|---|---|---|---|
| HotpotQA 多跳 | 两段全召回@10 | 0.79 | 0.92 | **0.89** | +13% |
| HotpotQA 高精度点 | F1@2 | 0.48 | 0.52 | **0.54** | +12% |
| **LoCoMo 对话** | micro-recall@5 | 0.514 | 0.460 | **0.560** | +9% |
| LoCoMo 对话 | 全证据@5 | 0.482 | 0.419 | **0.521** | +8% |
| sub2api 代码 | 难查询 rank-1 命中 | 0/3 | — | **2/3** | 质变 |
| HotpotQA(引擎API验证) | 两段全召回@10 | 0.73 | — | **0.90** | +23% |

**结论:**
1. **混合在每个领域都赢**,且不靠任何过滤/词库——在 sub2api 原始语料(含 i18n、测试文件)上,语义重排把 `DeductBalance`、`openai_account_scheduler.go` 顶到 rank-1。
2. **小模型(130MB)单用经常输给 BM25**(对话 0.46<0.51);价值在**融合**,提升幅度 **+8~23%**,是「显著但非颠覆」。
3. 文献预期:换 **Qwen3-Embedding-0.6B**(经 Zvec)可再上一个台阶(MTEB-Code SOTA,+15~25%)。

## 2. 内存/磁盘 现状与「能否压到 50MB」

实测(sub2api 全量,50,133 块):

| 阶段 | 时间 | 峰值内存 | 磁盘 |
|---|---|---|---|
| 建索引+落盘 | 39 s | **1,854 MB** | 621 MB |
| 单次查询 | ~10 ms | ~400 MB | 仅按需换页 |

**621MB 的真实字节构成(关键发现):**

| 子库 | 大小 | 原因 |
|---|---|---|
| **edges(关联图)** | **285.7 MB** | 自组织连边 32 条/节点 × JSON |
| post(倒排) | 128.5 MB | JSON 编码(可 varint 压 4×) |
| content(正文) | 52.6 MB | 分块正文(18 行重叠重复) |
| meta | 9.9 MB | JSON |

**能否 <50MB:能,但有前提。** 同样 50k 块的紧凑版投影:

| 组件 | 紧凑做法 | 大小 |
|---|---|---|
| 倒排 | varint 打包(替 JSON) | ~32 MB |
| 稠密向量 | int8 384维 (已实现) | 19.2 MB |
| meta | 定长打包 | ~3 MB |
| edges | 直查场景级联关闭→不存;或 varint | 0(或 ~40MB) |
| content | 不冗余存,按需回源文件 | 0 |
| **索引合计** | | **~54 MB**(再砍即 <50MB) |

- **索引数据 <50MB:可达**(varint 倒排 + int8 向量 + 不存正文/不过度连边)。典型项目(<3 万块)轻松 <50MB。
- **但真实 Transformer 模型是另一条底线**:bge-small 130MB。「模型+索引 <50MB」只有用**微型静态模型**(model2vec-2M ~8MB)才可能。
- 现状 1.85GB 建库内存 = **Python 对象开销 + 内存内建库 + JSON 膨胀 + 32 连边**,全部可工程化消除,但当前实现确实重。

## 3. 换纯 Rust 能否实现 <50MB?

| 维度 | Python 现状 | 纯 Rust 预期 |
|---|---|---|
| 运行时基线 | 解释器+numpy+onnx ~150-200MB | 无解释器,~数 MB |
| 建库峰值 | 1.85 GB(dict/str 开销) | 流式建库 + 紧凑 struct,**<100MB(可达 <50)** |
| 查询 RSS | ~400MB(大 JSON 倒排读) | mmap + varint 零拷贝,**<50MB** |
| 向量 | int8 | int8 + SIMD |
| 嵌入模型 | onnxruntime | `ort`/`candle`,量化静态模型 ~10MB |

**结论:纯 Rust 让「索引+查询 <50MB 运行时」现实可行**(mmap + varint + int8 + 静态量化嵌入);**唯一无法绕开的是真实 Transformer 的权重体积**——这与语言无关。

## 4. 你问的 Zvec(阿里 z 开头项目)

[**Alibaba Zvec**](https://github.com/alibaba/zvec)(2026-02 开源,`pip install zvec`,基于 Proxima)是**嵌入式向量数据库**(「向量界的 SQLite」),不是嵌入模型。已确认可安装(v0.5.1),内置 **BM25 + 稠密 + Qwen3-Embedding + HNSW/DiskANN + RRF 重排** 的完整混合检索。它正是 NebulaMem 蓝图原本引用的组件——**用它替换我们手写的 LMDB+倒排,可直接获得生产级混合检索 + Qwen 强嵌入**,我们的「激活扩散/侧向抑制」图层叠加其上即可。预期强度明显高于当前 bge-small 方案。

## 6. 原始设计(LLM提取 + Zvec + LadybugDB + LMDB)效果会怎么样?

利用 LoCoMo 自带的 **LLM 抽取事实**(`observation`,每条事实带证据 turn)直接实测「LLM 提取」这一臂(无需我跑 LLM):

| 索引方式 × 检索 | micro-recall@5 | 全证据@5 |
|---|---|---|
| 原始对话 turn + BM25 | 0.514 | 0.482 |
| 原始对话 turn + **混合** | **0.560** | **0.521** |
| **LLM抽取事实** + BM25 | 0.499 | 0.465 |
| **LLM抽取事实** + 混合 | 0.541 | 0.499 |

**反直觉但真实的结论:就「检索召回」而言,LLM 提取并不更好,反而略降(0.560→0.541)。** 因为抽取会丢失原始 turn 里命中问题的关键词,而稠密种子(Zvec 的价值)我们的混合已经吃到了。三个数据库本身(向量=我们的稠密、图=我们的激活扩散、KV=LMDB)相对当前方案**几乎不增加检索召回**。

**那原始重型设计赢在哪?**(以下为文献投影,非本机实测——需 LLM judge)
- **最终问答准确率**:LLM 把脏对话蒸馏成干净原子事实喂给模型 → Mem0 LoCoMo QA **66.9%(2025)→92.5%(2026)**。这是它真正的优势,**不在检索、在生成**。
- **去重/冲突消解/时序归一**:LLM 提取天然产出结构化、去冗余的事实。
- **Token 效率**:喂给模型的是短事实而非整段对话。

**代价(对照我们零依赖方案):**

| 维度 | 原始重型(LLM+3DB) | 当前混合(BM25+小向量+图) |
|---|---|---|
| 每条记忆写入 | 一次 LLM 调用(秒级 + $) | 毫秒、免费 |
| 检索召回 | ≈ 我们(甚至略低) | recall@5 0.56 |
| 问答准确率 | **更高**(干净事实) | 取决于下游 LLM 自己筛 |
| 本地/隐私/确定性 | 否(依赖 LLM、非确定) | **是**(纯本地、确定) |
| build 成本 | 高(全量 LLM 提取) | 39s/5万块 |

**最优解 = 两者结合:** 检索层保留我们的混合(便宜、本地、确定);把 LLM 提取做成**异步「梦境整理」**(蓝图原意),只对高频/将喂给模型的事实做离线蒸馏。既拿到 Mem0 级的事实干净度,又不为每次写入付 LLM 成本。

### 6.1 用面壁 MiniCPM-1B 做异步整理(真机实测)

实测 **MiniCPM5-1B(OpenBMB,Q4_K_M)** 经 `MemoryConsolidator(llm=...)` 钩子:

| 指标(CPU,本机) | 值 |
|---|---|
| 模型磁盘 | 657 MB |
| 峰值内存(模型+运行时) | ~1.1 GB |
| 单次整理延迟 | 0.7–1.0 s |
| 依赖 | 纯本地,无 API/网络 |

**结论:1B 是异步整理的理想选择**——整理是离线的,1s/1GB 无所谓;查询层仍零模型、毫秒级。**诚实caveat:1B 质量一般**:测试中把「学Rust/学了几周/掌握基础」只合并成「在学Rust」(丢了进展),Python→Rust 冲突没消解(两条都留)。机制 ✅、质量 ⚠️——问答提升是**部分的**,达不到 Mem0 的 92.5(那用 GPT-4 级)。可用 few-shot 提示或升到 MiniCPM 2B–4B 改善。

## 7. 诚实定位

- 「最优无模型 + 向量」**确实更好**,但小模型提升温和(+8~23%);要高准确率需强嵌入(Qwen3 via Zvec)。
- 我们**不是 SOTA**:Mem0(LLM)LoCoMo QA 92.5%;零模型 SuperLocalMemory 75-87%。注意我们报的是**检索 recall**,与 LoCoMo 的**QA 准确率**口径不同,不可直接对比。
- 当前实现**偏重**(建库 1.85GB),需 varint/紧凑化/Rust 才配得上「轻量」。方向正确,工程未到位。
